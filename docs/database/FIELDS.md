# Important fields

`SCHEMA.md` lists every column of every table. This document does the opposite job: it covers the
small number of fields whose *meaning* is not obvious from their type, where the entity mapping and
the service layer disagree with the obvious reading, or where getting it wrong causes a bug.

Everything below was checked against the entity classes and the service classes that write them.
Where a claim depends on a physical column name that Hibernate derives rather than the entity
declaring it, the name is marked `†`.

---

## Identity fields

Every table has a surrogate `Long` primary key generated by the database. The only exception is
`sessions`, which uses `GenerationType.AUTO`; on Hibernate 7 that resolves to a sequence, so its ids
arrive in blocks and gaps between them are normal and not a sign of deleted rows.

**Slugs are not a general feature of this schema.** Only four entities have one, and there is no slug
generation anywhere in the codebase. There is no `Slugify` helper, no `@PrePersist` that derives a
slug from a title, and no transliteration of Kurdish script. Slugs are typed by an admin, sent in the
request body, trimmed, and stored verbatim
([`AboutService.validateSlugs`](../../src/main/java/ak/dev/khi_backend/khi_app/service/about/AboutService.java),
[`ContactService.validateSlugs`](../../src/main/java/ak/dev/khi_backend/khi_app/service/contact/ContactService.java)).
Consequences worth stating plainly:

- **Editing a title after publication does nothing to the slug.** The two are unrelated fields. A slug
  only changes when someone edits the slug.
- **Editing a slug breaks every existing link to that page.** There is no redirect table, no slug
  history, and no 301 handling. `SitemapService` will emit the new URL and the old one simply 404s.
- Uniqueness is enforced per column, not per language pair. `About` and `Contact` additionally reject
  a request where `slugCkb` equals `slugKmr`.
- `ImageCollection` has the unique constraints but **no service-layer uniqueness check** — a duplicate
  slug reaches PostgreSQL and surfaces as a constraint-violation 500 rather than a validated 400.

The `{identifier}` path variable exists on exactly one endpoint,
`GET /api/v1/about/{identifier}`. `AboutService.getByIdentifier` tries `Long.valueOf(identifier)` and
falls back to a slug lookup on `NumberFormatException`. Contact and image collections have no such
endpoint — they expose `/slug/{slug}` only, and `/{id}` separately.

| Field | Tables | Type | Meaning and gotchas |
| --- | --- | --- | --- |
| `id` | all tables except `users_tbl`, `sessions` | `bigint` identity | `GenerationType.IDENTITY`. Dense, monotonic, never reused. |
| `user_id`† | `users_tbl` | `bigint` identity | The PK is named `user_id`, not `id`. Joins that assume `users_tbl.id` fail. |

| `nav_anchor_id` | `services` | `varchar(160)` | Slug-*shaped* but not a slug: it is the in-page `#anchor` for the services page. Validated against `^[A-Za-z0-9]+(?:-[A-Za-z0-9]+)*$` and checked for case-insensitive global uniqueness by `ServiceService.validateNavAnchorUnique`. |

## Bilingual content fields

The site has two Kurdish locales: `CKB` (Sorani) and `KMR` (Kurmanji). **Two structurally different
bilingual models coexist**, and code written for one does not work on the other.

**Model A — parallel columns on one row (the majority).** `About`, `Contact`, `News`, `Project`,
`Video`, `SoundTrack`, `ImageCollection`, `Writing`, `TeamMember`, `Partner`, `DonationSettings`,
`NavMenuItem` and `PublishmentTopic` all keep both languages side by side. Where an `@Embeddable`
content block is used (`AboutContent`, `NewsContent`, `ProjectContentBlock`, `VideoContent`,
`SoundTrackContent`, `ImageContent`, `WritingContent`), it is `@Embedded` **twice** with
`@AttributeOverrides`, producing `*_ckb` / `*_kmr` column pairs on the owning table. There is no
separate table for the embeddable — do not go looking for a `news_content` table.

**Model B — one child row per language (`Service` only).** `service_contents` holds a
`language_code` string column with a `UNIQUE(service_id, language_code)` constraint. This is
deliberately open: `language_code` is a plain `varchar(10)` validated only by
`@Pattern("^[A-Z]{2,5}$")`, so adding `EN` or `AR` needs no schema change. It is **not** the
`Language` enum, so it gets no `CHECK` constraint and nothing at the database level restricts it to
`CKB`/`KMR`.

Language-agnostic fields sit on the parent regardless of model: cover URLs on News/Project, phone
and map details on `contact_pages`, `location`/`service_type` on `services`, `sound_type`,
`publishment_year`, all the technical media metadata, and every `featured*` field.

**What `contentLanguages` actually does.** This is not a description of what happens to be filled in —
it is authoritative input that the service acts on. `NewsService.applyContentByLanguages` reads the
declared set and, for any language *not* in it, sets that language's embedded content to `null` **and
clears that language's tags and keywords**. `ProjectService` does the same. So removing `KMR` from
`contentLanguages` on an update is a destructive operation that silently deletes Kurmanji title,
description, tags and keywords. Validation only checks that the declared languages have a title;
it never checks the reverse, so content for an undeclared language is discarded without an error.

**Missing translations at read time.** There is no global fallback. The main content endpoints return
whatever is stored, including `null` for the absent language — combined with
`spring.jackson.default-property-inclusion: non_null`, the key is simply absent from the JSON and the
frontend must handle it. The **only** place a fallback exists is the homepage carousel:
`SiteContentService.localized(ckb, kmr, useKmr)` returns the requested language and falls back to the
other one when it is blank, so a Sorani-only article still produces a slide on the Kurmanji homepage
with Sorani text.

## Rich-text body fields

Long-form content is **Tiptap-produced HTML stored as a `text` column**. It is not JSON, not
ProseMirror node JSON, and not Markdown. Verified: every writer runs the value through
[`TiptapHtmlProcessor.process`](../../src/main/java/ak/dev/khi_backend/khi_app/service/media/TiptapHtmlProcessor.java),
which pattern-matches HTML attributes (`src="…"`, `href="…"`) with regexes — that only works on
markup — and every column is `columnDefinition = "TEXT"` or a plain long `varchar`.

`TiptapHtmlProcessor` does one job before persistence: it finds inline base64 data URIs and hoists
them to S3.

1. Early-out if the string is null, blank, or contains no `data:` — the processor is idempotent, so
   re-saving already-processed HTML costs nothing.
2. `DATA_URI_SRC` matches `src="data:<mime>;base64,…"` on `<img>`, `<video>`, `<audio>` and
   `<source>`; `DATA_URI_HREF` matches `href="data:…"` on `<a>` for PDFs and other downloads.
3. Each payload is base64-decoded, given a synthetic filename `tiptap-<nanoTime>.<ext>`, uploaded via
   `S3Service.upload`, and the attribute is rewritten to the returned public URL.
4. Failures are swallowed per-attribute: a malformed base64 payload or a failed upload is logged and
   the original `data:` attribute is left in the HTML. **The save still succeeds**, so a row can
   legitimately contain a multi-megabyte base64 blob inline in the `text` column.

> **Security note:** none of this HTML is sanitised. `pom.xml` contains no jsoup, no OWASP Java HTML
> Sanitizer, and no other HTML-cleaning dependency, and `TiptapHtmlProcessor` only rewrites `data:`
> URIs — it does not strip tags or attributes. `<script>`, `onerror=`, `<iframe src="javascript:…">`
> and everything else pass through untouched and are stored verbatim, then served back to browsers by
> the public read endpoints. The only control is authorisation: `SecurityConfig` restricts these
> writes to `EMPLOYEE`, `ADMIN` and `SUPER_ADMIN`, so the stored XSS is currently
> authenticated-author-only. That makes it a privilege-escalation path (an `EMPLOYEE` can plant a
> script that runs in a `SUPER_ADMIN` dashboard session), not a fully public one. If these fields are
> ever opened to less-trusted input, or if an `EMPLOYEE` account is compromised, there is nothing else
> in the way. Sanitising on write — and treating existing rows as untrusted — is the fix; escaping on
> render alone would break the legitimate markup these columns are meant to carry.

| Field | Tables | Type | Meaning and gotchas |
| --- | --- | --- | --- |
| `body_ckb`, `body_kmr` | `about_pages` | `text` | The About page has no hero image, no media gallery and no cover column any more. Every picture, video, voice clip and downloadable file is an inline element of this HTML. |
| `description` | `contact_pages` (per language), `service_contents` | `text` | Same pipeline. `service_contents.description` is the HTML one; `feature_description` is its plain-text twin. |
| `description_ckb`, `description_kmr` | `news`, `projects`, `videos`, `sound_tracks`, `image_collections`, `writings` | `text` | Processed through Tiptap on create and on update. On News and Project this replaced a former media table. |
| `description_ckb`, `description_kmr` | `image_album_items` | `text` | Per-image rich text, processed the same way. Note the sibling `caption_*` columns are `varchar(500)` and are *not* HTML. |
| `meta_description_ckb`, `meta_description_kmr` | `about_pages` | `varchar(2500)` | Not `text`. The `@AttributeOverride` on `About` supplies `length = 2500` but drops the embeddable's `columnDefinition = "TEXT"`, so anything longer than 2500 characters fails at insert. The `body` override does repeat `columnDefinition` and stays `text`. |

## Media and S3 fields

**Every media column in this schema stores a full public HTTPS URL, never a bare object key.** There
is no column anywhere holding an S3 key. `S3Service.getPublicUrl(key)` builds the URL at upload time
and `S3Service.extractKeyFromUrl(url)` parses the key back out when something needs deleting.

Key layout, from `S3Service.generateKey`:

```
https://s3-khiwebsite.s3.us-east-1.amazonaws.com/khi-web-folders/<folder>/<uuid>-<sanitised-filename>
                                                 └── aws.s3.base-folder ──┘
```

`<folder>` is one of `images`, `video`, `audio`, `files` — chosen from the MIME type by
`detectFolder`, or from an explicit `ProjectMediaType`. Album covers get their own nesting:
`khi-web-folders/albums/covers/{ckb|kmr}/…` and `khi-web-folders/albums/hover/…`. The filename is
sanitised with `[^a-zA-Z0-9._-] → _`, so non-Latin original filenames become runs of underscores; the
UUID prefix is what actually keeps keys unique.

Two consequences of storing URLs rather than keys:

- Changing the bucket name, region, or putting a CDN hostname in front of S3 breaks deletion for
  every pre-existing row, because `extractKeyFromUrl` string-matches on the stored host and
  `base-folder`.
- `external_url` and `embed_url` columns hold third-party URLs (YouTube, SoundCloud) and are **not**
  S3. `isOurS3Url` exists to tell them apart but is not called on the delete path.

**What happens to the S3 object when a row is deleted: nothing.** This is the important finding of
this section. Grepping every call site of `s3Service.deleteFile` / `deleteFiles` / `deleteByKey`
across `src/main/java` returns exactly four production callers:

- `UserProfileService` — deletes the previous profile image when it is replaced.
- `VideoService` / `SoundTrackService` — delete the previous *reklam* background video when it is
  replaced.
- `MediaService.delete` — the explicit admin-only `DELETE /api/v1/media` endpoint.

`NewsService.deleteNews`, `ImageCollectionService.delete`, and the delete paths on Project, Writing,
Video, SoundTrack, About, Contact and Service all delete the database row and leave every uploaded
object in the bucket forever. Deleting a photo story with 200 images orphans 200 objects. There is no
reaper job — a repo-wide grep for `@Scheduled` returns nothing. Storage cost grows monotonically and
the bucket is the only remaining copy of material that is no longer reachable from the application.

## Flag fields

There is **no draft/published workflow anywhere in this system**. None of the six publication types
(`news`, `projects`, `videos`, `sound_tracks`, `image_collections`, `writings`) has an `active`,
`published` or `status` column. Creating a row publishes it: the public list endpoints select
everything. `services.published_at` is a display timestamp, not a gate — nothing filters on it, it is
only a sort key.

`active` exists only on the pages and site-configuration tables, and it *is* honoured:
`AboutRepository` / `ContactRepository` expose `findAllByActiveTrueOrderByDisplayOrderAsc`,
`ServiceRepository` has active-only id scans, and `TeamMemberRepository`, `PartnerRepository`,
`SocialLinkRepository`, `NavMenuItemRepository` all have `findAllByActiveTrue…` variants. The
dashboard reads the unfiltered variants.

`featured` is one flag with two different meanings, split at `SiteContentService`:

- **Carousel slides** — News, Project, Writing, Video, SoundTrack, ImageCollection, and the singleton
  `donation_settings`. `countAllFeatured()` sums these seven sources and the toggle refuses to turn
  `featured` on once the total reaches `site_settings.max_featured_slides` (default 7). The guard is
  `turningOn && !entity.isFeatured() && …`, so re-ordering an already-featured record skips the check.
- **Page-level highlights** — `about_pages` and `services`. Deliberately excluded from the cap and
  from `getFeatured()`; featuring nine services can never block featuring an article. They are read
  through their own endpoints instead. Both still require an image before they can be featured.

**`featured_items` does not participate in any of this.** The entity is real so Hibernate creates the
table, but `FeaturedItemRepository` is injected into nothing — a repo-wide grep for `FeaturedItem`
matches only the entity and its own repository. The homepage carousel is computed in memory from the
`featured` / `featured_order` / `feature_image_url` columns on the content tables. The table is empty
on a fresh database and stale wherever rows were inserted by hand. Its `type` + `slug` pair is a
polymorphic pointer with no id column, no FK, and no validator, because nothing writes to it.

> **Correctness note:** several of these flags are Java primitive `boolean` fields declared without
> `nullable = false`, so Hibernate generates a nullable column. Under `ddl-auto: update`, adding such
> a column to a table that already has rows leaves them `NULL`, and Hibernate cannot map `NULL` into a
> primitive — every subsequent read of the table throws. That is exactly the production outage
> [`scripts/sql/2026-08-17-featured-about-service-donation.sql`](../../scripts/sql/2026-08-17-featured-about-service-donation.sql)
> was written to repair. `about_pages.featured`, `services.featured` and `donation_settings.featured`
> have since been hardened with `nullable = false` + `@ColumnDefault("false")`. Still exposed:
> `services.active`, `featured_items.active`, `team_members.active`, `partners.active`,
> `social_links.active`, `nav_menu_items.active`, `nav_menu_links.active`,
> `donation_settings.financial_enabled` and `archive_enabled`, plus `news.featured` and
> `projects.featured` (primitive, no `@Column` at all, so `NOT NULL` with no default — which under
> `ddl-auto: update` on a non-empty table fails the `ALTER`, gets logged, and leaves the column
> *absent*). Verify these against the live database before the next release.

## Ordering and position fields

Three different ordering mechanisms coexist and they behave differently.

**Hibernate-managed `@OrderColumn`** — the only place where position is genuinely maintained by the
persistence layer. `video_source_files`, `video_cast_members`, `video_highlight_clips`,
`service_gallery_media`, `service_feature_images`, `service_thumbnail_images` and `service_partners`
all use `@OrderColumn(name = "display_order")`. These are **dense and 0-based**, and Hibernate
guarantees it by rewriting the whole collection: the element collections have no independent
identity, so an insert in the middle deletes and reinserts the affected rows.

**`@OrderBy` on a real child collection** — position is *read* from a column but never written by
Hibernate. `SoundTrack.files` and `SoundTrack.attachments` use `@OrderBy("id ASC")`,
`ImageCollection.imageAlbum` uses `@OrderBy("sortOrder ASC")`, `Video.videoClipItems` uses
`@OrderBy("clipNumber ASC")`, `Writing.seriesBooks` uses `@OrderBy("seriesOrder ASC")`.

**Plain integer columns sorted by a repository query** — `display_order` on `about_pages`,
`contact_pages`, `team_members`, `partners`, `social_links`, `nav_menu_items`, `nav_menu_links`.

Where the caller supplies the value there is nothing enforcing density or uniqueness: two rows can
share a `display_order`, and the tie-break is whatever the query's secondary sort says (`id ASC` for
nav menu items, nothing at all for team members and partners — that ordering is not stable).
Inserting in the middle means renumbering by hand from the client.

> **Correctness note:** `sound_track_brochures.brochure_order` and
> `sound_track_attachments.attachment_order` are inert. Both entities carry javadoc claiming they are
> "managed automatically by `@OrderColumn`", but there is no `@OrderColumn` anywhere in the sound
> module — both parent collections use `@OrderBy("id ASC")`. Hibernate never reads or writes either
> column. Display order is really insertion order by id, and anything setting these columns expecting
> them to take effect is writing to dead storage.

Written by Hibernate. Never set it yourself. |
| `display_order` (plain column) | `about_pages`, `contact_pages`, `team_members`, `partners`, `social_links`, `nav_menu_items`, `nav_menu_links`, `featured_items` | `integer` | Caller-supplied, defaults to `0` on most entities. | `sort_order` | `services` | `integer` NULL | Nav/scroll order for the public services page. `NULL` sorts last via `COALESCE(s.sortOrder, 2147483647)` — which also means the declared `idx_service_sort_order` cannot serve the sort. |
| `clip_number` | `video_clip_items` | `integer` NULL | Entirely caller-supplied, nullable, no uniqueness. The `@OrderBy("clipNumber ASC")` puts `NULL`s last on PostgreSQL. |
| `series_order` | `writings` | `double precision` | The one field designed for mid-sequence insertion: fractional values let you slot a volume between 1.0 and 2.0 without renumbering. Defaults to `1.0` in `@PrePersist` when not supplied, so most books share the value 1.0. |
| `brochure_order`, `attachment_order` | `sound_track_brochures`, `sound_track_attachments` | `integer` | Dead columns — see the note above. |
| `featured_order` | the featured tables | `integer` NULL | Not a display order in the same sense: it is a preference, and `getFeatured()` renumbers the final slide list `1..N` before returning it. Whatever integers you store, the API always emits a dense 1-based `displayOrder`. |

## Timestamp and audit fields

Four different mechanisms populate timestamps in this schema, and only one of them records *who*.

1. **Spring Data JPA auditing** via
   [`AuditableEntity`](../../src/main/java/ak/dev/khi_backend/khi_app/model/audit/AuditableEntity.java) —
   `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, `@LastModifiedBy`, enabled by
   [`AuditingConfig`](../../src/main/java/ak/dev/khi_backend/khi_app/config/AuditingConfig.java) and fed
   by [`AuditorAwareImpl`](../../src/main/java/ak/dev/khi_backend/khi_app/config/AuditorAwareImpl.java).
   **Exactly one entity extends it: `Project`.** So `projects` is the only table in the entire
   database with `created_by` / `updated_by` columns.
2. **Hibernate `@CreationTimestamp` / `@UpdateTimestamp`** — About, Contact, Service, `featured_items`,
   and `created_at` on the three submission tables.
3. **Hand-written `@PrePersist` / `@PreUpdate`** — News, all four publishment types,
   `publishment_topics`, `site_settings.touch()`.
4. **Set in the service layer** — `ProjectLog.createdAt` has no lifecycle callback at all; a caller
   that forgets hits a `NOT NULL` violation. `users_tbl.created_at` / `updated_at` are hand-maintained
   by `UserService` and `UserProfileService`, are nullable, and go stale on any write that bypasses
   those two classes.

**What `created_by` holds.** `AuditorAwareImpl.getCurrentAuditor()` returns the Spring Security
principal name, or the literal string **`"SYSTEM"`** when the authentication is null, unauthenticated,
or an `AnonymousAuthenticationToken`. Two things follow. First, since only `Project` is audited and
project writes require `EMPLOYEE`+, `"SYSTEM"` in `projects.created_by` means a write that happened
outside a request thread, not a public submission. Second, **there is no `created_by` on the public
submission tables at all** — an anonymous contact message or donation pledge records only
`created_at`. The four log tables (`news_audit_logs`, `service_audit_logs`, `video_logs`,
`sound_track_logs`, `writing_logs`, `image_collection_logs`, `project_log`) store a free-text
`performed_by` / actor string, frequently the literal `"system"`, with no foreign key to `users_tbl`.
So for everything except `projects`, "which admin changed this" is not recorded anywhere.

**The UTC / Asia/Baghdad split is narrower than it looks.** `application.yaml` sets
`spring.jpa.properties.hibernate.jdbc.time_zone: UTC` and `spring.jackson.time-zone: Asia/Baghdad`.
But almost every timestamp column in this schema is mapped from `java.time.LocalDateTime`, which
carries no zone:

- Hibernate's `jdbc.time_zone: UTC` governs how zoned values are bound to JDBC. It does not convert a
  `LocalDateTime`, which is a wall-clock value written as-is.
- `@CreationTimestamp` / `LocalDateTime.now()` read the **JVM default zone**. On a UTC container these
  are UTC; on a `TZ=Asia/Baghdad` container they are Baghdad local time, three hours ahead, with no
  marker in the data saying which. `site_settings.touch()` and every `@PrePersist` in the publishment
  module have this property.
- Jackson's `Asia/Baghdad` context zone cannot be applied to a `LocalDateTime` either, so these
  columns serialise as a bare `yyyy-MM-dd HH:mm:ss` string with no offset. The Baghdad setting only
  affects types that carry a zone.
- The `Instant` columns on `users_tbl` and `sessions` *are* true UTC instants and serialise with a `Z`.

Net effect: the same JSON response can mix genuine UTC instants and unlabelled local-time values, and
comparing `users_tbl.created_at` against `projects.created_at` is only valid if the app server runs in
UTC.

| Field | Tables | Type | Meaning and gotchas |
| --- | --- | --- | --- |
| `created_at`, `updated_at` | `projects` | `timestamp NOT NULL` | The only Spring Data-audited pair. `created_at` is `updatable = false`. |
| `created_by`, `updated_by` | `projects` only | `varchar(120)` | `created_by` is `updatable = false`. Holds the JWT subject, or `"SYSTEM"`. No other table in the database has these columns. |
| `created_at`, `updated_at` | About, Contact, Service, News, all publishment tables, `publishment_topics` | `timestamp` | JVM-local wall clock, not necessarily UTC. Mechanism differs per module (see above) but the storage is identical. |
| `created_at`, `updated_at` | `users_tbl` | `timestamptz` (`Instant`) | Nullable and hand-maintained. `User` does not extend `AuditableEntity`; every mutation must call `setUpdatedAt(Instant.now())` explicitly, and rows created outside `UserService` / `UserProfileService` have both `NULL`. |
| `login_timestamp`, `expires_at`, `logout_timestamp` | `sessions` | `timestamptz` (`Instant`) | Genuine UTC instants. Nothing ever deletes expired sessions; logout only flips `is_active`. |
| `published_at` | `services` | `timestamp` NULL | Admin-set publication date. `NULL` means "never formally published" but does **not** hide the row. |
| `date_published` | `news` | `date` | A `LocalDate`, not a timestamp. Defaulted to `LocalDate.now()` in `@PrePersist` when absent. The declared index uses the Java property name `datePublished DESC`; Hibernate runs that token through the naming strategy so the DDL is correct today, but a rename would silently produce an index on a non-existent column. |
| `timestamp` | `video_logs`, `image_collection_logs` | `timestamp` | Column literally named `timestamp`. PostgreSQL accepts it unquoted; some tools will not. |
| `reset_token_expiration`, `lock_time`, `password_expiry_date` | `users_tbl` | `timestamptz` (`Instant`) | Security-relevant deadlines, all true instants. |

## Taxonomy fields

Five different taxonomy strategies, ranging from a proper vocabulary table to raw denormalised
strings. What they share is that **everything is created on demand** — there is no seeded reference
data and no admin step required before content can be filed.

**FK-backed and deduplicated.** `project_tags` and `project_keywords` are shared vocabularies:
`ProjectService.ensureTags` / `ensureKeywords` look a name up and insert it only if absent, then link
via one of four join tables (`project_tag_map_ckb`, `project_tag_map_kmr`, `project_keyword_map_ckb`,
`project_keyword_map_kmr`). One row per distinct name across both languages; the *language* lives in
which join table the row is referenced from, not on the tag.

**FK-backed and deduplicated, with an update side effect.** `news_categories` and
`news_sub_categories`. `NewsService.getOrCreateCategory` matches on `nameCkb` only and, when it finds
an existing row whose `nameKmr` differs from the request, **overwrites the stored Kurmanji name**. So
posting an article with a slightly different Kurmanji spelling silently renames the category for every
other article using it.

**FK-backed but not deduplicated.** `publishment_topics` is shared by all four publishment types and
partitioned by a free-text `entity_type` column (`VIDEO` / `SOUND` / `IMAGE` / `WRITING`).
`resolveOrCreateTopic` accepts either an existing `topicId` — validated to belong to the right
`entity_type`, otherwise a type-mismatch error — or an inline `newTopic`, which it **inserts
unconditionally with no lookup**. Sending the same topic name inline twice creates two topic rows.

**Raw denormalised strings.** News, Video, SoundTrack, ImageCollection and Writing keep tags and
keywords as `@ElementCollection<String>` side tables, one per language, per type. No vocabulary, no
dedup across articles, no FK. Because they are unordered `Set` collections, Hibernate gives these
tables only a foreign key — **no primary key and no unique constraint** — so uniqueness holds only in
memory and any writer outside JPA can insert duplicates.

**Free text on the parent row.** `services.service_type`, `sound_tracks.sound_type`,
`sound_track_files.genre` and `sound_track_files.form`.

| Field | Tables | Type | Meaning and gotchas |
| --- | --- | --- | --- |
| `category_id`, `sub_category_id` | `news` | `bigint NOT NULL`, FK | `@ManyToOne(optional = false)`. Both mandatory on every article. Deleting a category that still has articles raises an FK violation. |
| `name_ckb`, `name_kmr` | `news_categories`, `news_sub_categories` | `varchar` | `name_ckb` unique (globally on categories, per-parent on subcategories); `name_kmr` **not** unique, though the repositories query it expecting `Optional`. Also mutable as a side effect of creating an article — see above. |
| `topic_id` | `videos`, `sound_tracks`, `image_collections`, `writings` | `bigint` NULL, FK | Optional. No `ON DELETE` action anywhere, so deleting a referenced topic fails on the FK for all four. Only Video has an unlink helper (`VideoRepository.findByTopicId`, used by `deleteTopic()`). The `ImageCollection` javadoc proposes an `ON DELETE SET NULL` migration that Hibernate never generates. |
| `entity_type` | `publishment_topics` | `varchar(20) NOT NULL` | Free-text discriminator, not an enum, no `CHECK`. A typo produces a topic invisible to every lookup. |
| `name` | `project_tags`, `project_keywords` | `varchar`, unique | Unique but **case-sensitive**, while the repositories look up with `findByNameIgnoreCase` returning `Optional`. `Health` and `health` can both exist, after which the lookup throws `NonUniqueResultException`. A unique index on `lower(name)` would close it. |
| `tag_ckb` / `tag_kmr` | `news_tags_*`, `video_tags_*`, `sound_track_tags_*`, `image_tags_*`, `writing_tags_*` | `varchar` | Three different widths across five types: `varchar(100)` for Video and Image, `varchar(80)` for News and Writing, `varchar(60)` for Sound. A tag copied from an image collection to a sound track can be silently rejected. Keywords drift the same way: 150 for Video and Image, 120 for News and Writing, 100 for Sound. |
| `slug` | `book_genres` | `varchar(60) NOT NULL`, unique | The genre's stable machine key (editor-managed rows since 2026-09-03, replacing the `BookGenre` enum — see [`../BOOK_GENRES.md`](../BOOK_GENRES.md)). | `genre_ckb`, `genre_kmr` | `writings` | `varchar(150)` | Separate from the `book_genre_links` rows and unrelated to them: a free-text per-language genre label. Two genre concepts on the same entity. |
| `service_type` | `services` | `varchar(100) NOT NULL` | Deliberately free text so admins can invent types. `ServiceRepository.findActiveIdsByType` compares `lower(s.serviceType)`, which defeats `idx_service_type`. |
| `sound_type` | `sound_tracks` | `varchar(100) NOT NULL` | A `SoundType` enum (`LAWK`, `HAIRAN`) exists in `enums/publishment/` but is referenced by no mapping — the column is a plain `String`. Any value can be stored. `findIdsBySoundType` filters on `lower(sound_type)`, so the repository javadoc's claim that it "hits `idx_soundtrack_type`" is false. |
| `partner_id` | `service_partners` | `bigint` | An `@ElementCollection<Long>`, so **no foreign key to `partners`**. Deleting a partner leaves dangling references on service pages with no error. |

## Media metadata fields

> **Correctness note:**
> [`MediaMetadataExtractor`](../../src/main/java/ak/dev/khi_backend/khi_app/service/MediaMetadataExtractor.java)
> is dead code in production. It is a `@Component` with a full metadata-extractor implementation for
> images, video and audio, but a repo-wide grep finds it referenced only by its own two test classes —
> no service injects it and nothing calls `extract()`. Every field its javadoc describes as
> automatically populated is in fact caller-supplied, except image dimensions, which
> `ImageCollectionService` extracts itself with a separate `ImageIO` call.

So the honest split is:

**Genuinely extracted by the server** — only in
[`ImageCollectionService.extractAndSetImageMetadata`](../../src/main/java/ak/dev/khi_backend/khi_app/service/publishment/image/ImageCollectionService.java),
and only when the caller actually uploads a multipart file. It reads `file.getSize()` and
`file.getContentType()` from the multipart wrapper and decodes the bytes with `ImageIO.read` for
width and height. Failures are swallowed with a warning: an unsupported or corrupt image still saves,
with `width_px` and `height_px` left `NULL`. When an item's source is switched to an external URL,
`clearImageMetadata` nulls all four columns.

**Derived from the upload, not from the file's contents** — `sound_track_files.size_bytes` and
`sound_track_attachments.size_bytes` take `MultipartFile.getSize()` when a file is uploaded. That is
the HTTP payload size, not anything read out of the container.

**Everything else is whatever the client sent.** Duration, bitrate, sample rate, page count, video
dimensions: the client supplies them, the server trims and stores them. Nothing validates them against
the file, so an audio file can claim any duration at all.

| Field | Tables | Type | Meaning and gotchas |
| --- | --- | --- | --- |
| `width_px`, `height_px` | `image_album_items` | `integer` NULL | **Extracted** via `ImageIO` on upload. `NULL` for URL-sourced items and for formats `ImageIO` cannot decode. Pixels. `getAspectRatio()`, `isPortrait()` and `isLandscape()` are `@Transient` helpers computed from these — they are not columns. |
| `file_size_bytes` | `image_album_items` | `bigint` NULL | **Extracted** from `MultipartFile.getSize()`. Bytes. Nulled when the source becomes an external URL. |
| `mime_type` | `image_album_items` | `varchar(50)` NULL | **Extracted** — but from the client-declared `Content-Type` header, not from magic bytes. Do not treat it as trustworthy. |
| `size_bytes` | `sound_track_files`, `sound_track_attachments`, `film_reklam_videos`, `sound_reklam_videos` | `bigint NOT NULL` | Set from the multipart size on upload; otherwise the caller's `sizeBytes`, defaulting to `0`. `0` means unknown, not empty. Bytes. |
| `duration_seconds` | `sound_track_files` | `bigint NOT NULL` | **Caller-supplied.** `applyFileMetadata` copies the DTO value straight through; nothing decodes the audio. `0` means unknown. Whole seconds. |
| `duration_seconds` | `videos`, `video_source_files`, `video_highlight_clips` | `integer` NULL | **Caller-supplied.** Whole seconds. |
| `bit_rate` | `sound_track_files` | `varchar(50)` | **Caller-supplied free-text label**, not a number: the entity javadoc gives `"24-bit"`, `"320 kbps"` as examples. It conflates bit depth and bitrate. Not sortable or comparable without parsing. |
| `sample_rate` | `sound_track_files` | `varchar(50)` | **Caller-supplied free-text label** — `"44100 Hz"`. Same problem. |
| `audio_channel` | `sound_track_files` | `varchar(10)`, `@Enumerated(STRING)` | `MONO` / `STEREO`. Caller-supplied, nullable. The one properly typed technical field in the sound module. |
| `file_format` | `sound_track_files` | `varchar(50)` | Caller-supplied string (`"MP3"`, `"FLAC"`), deliberately not an enum so new formats need no migration. Note `file_type` on the same table *is* an enum — two overlapping format concepts. |
| `file_format_ckb`, `file_format_kmr` | `writings` | `varchar(20)`, `@Enumerated(STRING)` | `WritingFileFormat`. The `@Enumerated` survives the `@AttributeOverride`, which only renames the column. |
| `file_size_bytes_ckb/_kmr`, `page_count_ckb/_kmr` | `writings` | `bigint` / `integer` NULL | **Caller-supplied.** Nothing reads the PDF. Bytes and pages respectively. |

## Personal data fields

Four tables hold data about identifiable people. Three of them collect it from anonymous members of
the public.

**Read access.** `GET /api/v1/contact/messages`, `GET /api/v1/donations/financial` and
`GET /api/v1/donations/archive` are named explicitly as `hasAnyRole("ADMIN","SUPER_ADMIN")` in
`SecurityConfig`, *before* the blanket `.requestMatchers(HttpMethod.GET, "/api/v1/**").permitAll()`
further down the chain. The controller methods carry no `@PreAuthorize` of their own, so **that rule
ordering is the only thing protecting these three tables**. Moving the blanket rule up, or adding a
new GET route under these prefixes that is not covered by the explicit matcher, exposes visitor and
donor personal data publicly. `users_tbl` is reachable only through `/api/users/**`
(`SUPER_ADMIN`) and `/api/user/**` (the authenticated user's own record).

**Retention: there is none.** There is no `DELETE` endpoint for `contact_messages`,
`financial_donations` or `archive_donations` — only a status `PATCH`. No soft delete, no
anonymisation path, no scheduled purge (`@Scheduled` appears nowhere in the codebase). Rows are
permanent from the moment they are inserted. Anyone planning an erasure or export process starts from
zero. The same applies to `sessions` and `token_blacklist`, which grow by one row per login and per
logout forever.

**`NOT NULL` does not mean present.** `SiteContentService.orEmpty()` writes `""` rather than `NULL`
into `financial_donations.email`, `archive_donations.email`, `archive_donations.title` and
`archive_donations.description` when the optional API field is absent. Any reporting, deduplication or
subject-access search over these columns must treat `""` as missing.
